4.2 Protocolo CANopen

Traducción de la sección 4.2 del manual GIM6010-8 rev 2.2 (págs. 54–56 del original).

CANopen es una especificación de protocolo de comunicación para el ámbito de la automatización. Este producto la implementa conforme a las normas CiA 301, CiA 302 y CiA 402. Antes de usar el protocolo CANopen del producto, cambie el protocolo del CAN a CANopen con el siguiente comando de odrivetool:

odrv0.can.config.protocol = 2

4.2.1 Archivo de descripción del dispositivo (EDS)

El archivo EDS describe las funciones y los parámetros de comunicación del dispositivo. Para comunicarse con este producto por CANopen hay que importar su archivo EDS, que puede descargarse en: https://bl.cyberbeast.cn/actuator/cb_0.1.eds

4.2.2 Formato de las tramas del protocolo

CANopen se basa en el CAN estándar: su ID de 11 bits se divide en un código de función de 4 bits y un ID de nodo (node_id) de 7 bits, lo que permite hasta 127 nodos en el bus (el 0 se reserva para la difusión). El formato de trama es el siguiente:

SegmentoBit10 ~ Bit7Bit6 ~ Bit0Byte0 ~ Byte7
DescripciónCódigo de funciónnode_idDatos de la comunicación

4.2.3 Mensajes

El formato de los mensajes varía según el CAN ID (COB-ID).

4.2.3.1 NMT (gestión de red)

NMT sirve para ordenar cambios de estado a todos los nodos del bus o a uno concreto. Su COB-ID es siempre 0 y sus datos ocupan 2 bytes:

COB-IDData Byte0Data Byte1
0x000Palabra de comando de estadonode_id

Las palabras de comando de estado son:

Palabra de comandoDescripción
0x01Cambiar al estado «operational»
0x02Cambiar al estado «stopped»
0x80Cambiar al estado «pre-operational»
0x81Reiniciar el nodo («reset node»)
0x82Reiniciar la comunicación («reset communication»)

Por ejemplo, tras conectarse al driver, el usuario envía primero el siguiente comando NMT para poner en marcha todos los nodos del bus:

COB-IDDatos
0x00001 00

4.2.3.2 SYNC

La función de sincronización sirve para sincronizar todos los nodos del bus; se usa sobre todo para sincronizar los mensajes PDO. Su COB-ID es siempre 0x80 y el campo de datos va vacío.

Por ejemplo, después de poner en marcha los nodos con el comando NMT, lo habitual es enviar el mensaje SYNC para que los nodos empiecen a transmitir datos PDO.

4.2.3.3 PDO

El PDO es el mecanismo de comunicación pensado para la transmisión de datos en tiempo real: se emplea tanto cuando el usuario quiere obtener datos del nodo de forma periódica como cuando quiere que este los notifique por eventos. El PDO solo puede usarse cuando el nodo está en estado «operational», así que primero hay que cambiar su estado con un mensaje NMT.

El formato del campo de datos de los mensajes PDO depende de su estructura de mapeo, que no es estándar, sino que la define el archivo EDS.

4.2.3.4 SDO

La comunicación SDO permite acceder a los datos del diccionario de objetos del producto (diccionario definido por el EDS). Esos datos pueden entenderse como la información de parámetros del producto. En general, el SDO se usa solo durante la configuración y no para el intercambio de datos en marcha; para el intercambio de datos en tiempo real se recomienda el PDO.

4.2.3.5 NMT (latido)

El mensaje de latido se limita a anunciar en el bus el estado del nodo, indicando que funciona con normalidad. Su formato de trama es:

COB-IDData Byte0
0x700 + node_idEstado
